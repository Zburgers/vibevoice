# Whisper pipeline audit and performance measurements

Date: October 3, 2026. Initial audit branch: `codex/pill-revamp-v0.2.8`.
The changes are submitted from `codex/whisper-pipeline-v0.2.8` against
`codex/v0.2.8`.
These changes sit alongside pre-existing clipboard, control-page, equalizer,
and packaging changes in the working tree. They are not release publication.

This records the initial audit before the engine update. The subsequent
[component updater work](v0.2.8-whisper-updater.md) activates 1.9.4, advances
the setup-script pins and includes a fresh comparison; use that report for
the current installed version.

## Engine and execution path

The Windows engine discovered from automatic settings is
`%LOCALAPPDATA%/VibeVoice/engines/whisper.cpp/build/bin/Release/whisper-cli.exe`,
with `models/ggml-base.en.bin`. The installed checkout is
`df7638d8229a243af8a4b5a8ae557e0d74e0a0ae`; its source and generated Release
project identify Whisper **1.8.6**; an isolated DLL load and direct call to
its exported `whisper_version()` also returned **1.8.6**. The installed
base.en SHA-256 matches the pinned
`a03779c86df3323075f5e796cb2ce5029f00ec8869eee3fdfb897afe36c6d002`.
Its actual inference log reports AVX,
AVX2, F16C, FMA, OpenMP, and CPU execution; no OpenVINO or CoreML. Cache
booleans reporting AVX2=OFF are misleading here: native feature detection
adds AVX2 to the compiled target, and the runtime log confirms it.

Both setup scripts target the **v1.9.3** tag. A separate tag checkout/build
resolved `v1.9.3^{commit}` to
`371b5a7561823ab2bb32142d2751e35e7534727b` (its CMake version includes a
`1.9.3-dev` suffix). Neither the installed engine nor the model was replaced.

Windows/macOS: CPAL callback downmixes the default device stream to mono
16-bit PCM, sends sample batches to a writer thread, writes a WAV at the
native device sample rate, then finalizes it on Stop. Whisper/miniaudio
decodes/resamples to 16 kHz. Linux uses pw-record, arecord, or ffmpeg at
16 kHz. After Stop, a background worker starts a fresh CLI process, loads
the model, transcribes the entire recording, reads the temporary text file,
applies text cleanup/dictionary rules, inserts through the clipboard
transaction, optionally saves history, and cleans the temporary files.

The existing CLI options leave beam size=5, best-of=5, temperature fallback,
English language, and model accuracy unchanged. The application previously
relied on the CLI default thread count (4 on this machine). Cancellation
and timeout polling runs every 20 ms; it is not the major source of latency.
The equalizer emitter stops when recording ends; it is not an ongoing
transcription-time CPU workload.

## Measurements

Host: Intel i5-8350U, 4 physical cores / 8 logical processors, 16 GB RAM.
Fixture: the engine's 11-second JFK WAV. Two sequential repeats per
configuration, same base.en model and decoding settings. Timing logs are
enabled in the profiling script, whereas the app suppresses CLI prints.
Average CPU percentage is process CPU-seconds / wall-seconds / 8 * 100;
it is an average, not a peak or the Task Manager process-group reading.
Memory is the largest sampled working set at 100 ms intervals.

| Installed 1.8.6 configuration | Mean wall time | Mean CPU time | Mean CPU share | Sampled memory |
| --- | ---: | ---: | ---: | ---: |
| Existing CLI defaults | 4.68 s | 16.90 CPU-s | 45.1% | about 300 MB |
| 4 threads, passive OpenMP wait | 4.36 s | 14.77 CPU-s | 42.3% | about 299 MB |
| 2 threads, passive OpenMP wait | 5.97 s | 10.98 CPU-s | 23.0% | about 299 MB |
| 1 thread, passive OpenMP wait | 9.69 s | 9.56 CPU-s | 12.3% | about 298 MB |

All eight transcripts were identical. Runs with the passive hint were about
7% faster and consumed about 13% fewer CPU-seconds in this small sample. The
installed DLL links VCOMP140 (MSVC OpenMP 2.0); Microsoft's documented
environment variables do not include OMP_WAIT_POLICY. Honoring that hint
has not been established here, so the difference cannot be attributed to
sleeping workers and may reflect run order, warm-up, or scheduling. See
[Microsoft's OpenMP environment documentation](https://learn.microsoft.com/en-us/cpp/parallel/openmp/reference/openmp-environment-variables?view=msvc-170)
and the [OpenMP wait-policy specification](https://www.openmp.org/wp-content/uploads/OpenMP-API-Specification-5.0.pdf),
which defines a runtime hint. These are
preliminary observations, not a general speedup guarantee or an accuracy
qualification for the owner's speech. The 2-thread setting reduces CPU
share substantially but took about 27% longer; a hard CPU limit cannot
promise lower usage and lower latency simultaneously on this CPU backend.

First default run: model load 328 ms, mel 27 ms, encoder 2750 ms, beam batch
decode 807 ms, token sampling 262 ms, total engine time 4257 ms. Encoding
dominates; keeping the model resident would save roughly the load time,
not the entire delay. Whisper normally uses a full audio context even for
short speech. Shortening that context, reducing beams, or disabling
fallback can affect recognition and were not made default optimizations.

The isolated v1.9.3 build produced the same transcript. Its 4-thread
passive runs were 4.37 s and 4.24 s, close to the installed engine. Later
low-thread runs were increasingly affected by host activity. There is no
evidence here that upgrading alone substantially improves latency.

A local Q5_0 model trial reduced sampled memory to about 207 MB, but
recorded 83–103-second runs. Other native transcription/build activity
overlapped later measurements, so these timings cannot isolate a
quantization regression. The experimental run was stopped and its partial
results retained; quantization is not activated or advertised as faster.

A v1.9.3 build using the native worker pool (`GGML_OPENMP=OFF`) was also
tested. Its four-thread runs took 24.95 s and 4.15 s; its two-thread runs
took 8.74 s and 5.86 s, all with the identical sample transcript. A separate
Rust release compilation remained active during this trial. Retain the
slow receipts: this is not a qualified backend speedup. Adjacent installed
engine baseline runs took 4.59 s and 4.62 s. No backend was switched.

Raw timing logs/transcripts/results are in `outputs/whisper-performance/`,
including the separate v1.9.3 and partial Q5 trials. They are local profiling
artifacts, not uploaded audio. Reproduce with PowerShell 7:

```powershell
pwsh -NoProfile -File scripts/benchmark-whisper.ps1 -Repeats 2
```

Use `-AudioPath` for a consented representative recording, `-ModelPath`
for a candidate model, and `-VariantNames default,passive-4,passive-2` to
omit the slowest case. The installed engine directory is the default;
`-EngineRoot` selects a separate build and `-CliPath` supports a different
build directory. The script records input/binary/DLL hashes and now refuses
an active Whisper/compiler process unless `-AllowBusyHost` is explicitly
set. The exploratory trials above preceded that safeguard. Avoid other
concurrent CPU-heavy work as well.

## Confirmed defects and fixes

1. **Repeated Stop admits overlapping sessions.** While Processing, the
   runtime has no recording session. A second Stop previously set Ready
   and an error, permitting a new recording while the original worker
   still owned transcription/insertion. Its completion could overwrite
   newer state or insert an older transcript. Stop now rejects Processing
   without changing state; the normal start gate continues to block it.
2. **Late Cancel can still paste.** The child polling loop checks Cancel,
   but successful child completion and text cleanup previously proceeded
   to clipboard insertion without a cancellation commit boundary. Cancel
   and insertion now arbitrate with the same token mutex. A Cancel
   acknowledged first prevents insertion; after insertion is claimed,
   Cancel returns that there is no cancellable transcription. This is a
   defined boundary, not a promise to undo an already-started paste.
3. **Audio callback can race the writer Stop sentinel.** Stream pause does
   not establish callback completion. Native stream destruction now
   precedes writer Stop/join. CPAL's Windows WASAPI Drop sends Terminate
   and joins its audio worker, establishing that no later callback can
   enqueue samples behind Stop. macOS uses its native stream teardown;
   physical macOS capture validation remains pending.
4. **Preparation failures leave artifacts/unjoined writer work.** Stream
   creation and play errors now stop/join the writer and remove the
   temporary WAV instead of relying on detached thread/channel cleanup.
5. **History duration includes processing time.** The old duration was
   session wall time through inference/paste. New history entries use
   finalized WAV frame count/sample rate; old entries are unchanged.
6. **Setup compares an annotated tag object to a commit.** Both installers
   pinned `7246b731...`, the v1.9.3 annotated tag object, but checked
   `git rev-parse HEAD`. They now pin the peeled commit `371b5a756...`,
   retaining fail-closed verification. Fresh full installation was not run.
7. **No resource visibility or CPU budget.** Settings now exposes automatic
   (up to 4), 1, 2, and 4 threads, bounded to available logical CPUs (and a
   maximum explicit 16). Existing settings default to automatic. Child-only
   `OMP_WAIT_POLICY=PASSIVE` requests passive waiting where supported and
   avoids changing the user's environment; runtime support is not assumed.

Diagnostics shows last completed inference duration, audio duration,
thread count, and Windows process CPU time/average CPU share/peak memory.
The copyable support report includes numeric metrics only. These metrics
are in-memory; transcript contents are not added to telemetry. Non-Windows
CPU/memory measurements remain unavailable instead of reporting zero.
Metrics cover the CLI process, not GPU utilization or total VibeVoice CPU.

## Remaining limitations and opportunities

- Microphone callback errors are logged, not promoted into capture state;
  a device disconnect after some audio could yield a partial transcript.
- The audio writer channel is unbounded. Long captures or a stalled disk
  can grow queued memory; a bounded design must report overload rather
  than silently discard speech or block the real-time callback.
- Writer file creation happens asynchronously; a storage failure can be
  reported at Stop after the owner has spoken, rather than rejecting Record
  immediately. A readiness handshake would improve this failure path.
- CLI stderr is suppressed. Nonzero exits provide status without detailed
  engine diagnosis; bounded/redacted error categorization would improve
  support without leaking transcript-bearing output.
- Settings/dictionary are loaded at Stop, rather than frozen at Record;
  changes during a recording apply to that recording. This behavior is
  not changed here.
- Silence is transcribed with normal Whisper no-speech behavior. VAD needs
  a separately verified model and tests that quiet speech is preserved.
- A resident engine, OpenVINO/Vulkan/GPU backends, and alternative
  quantization need representative accuracy/latency validation on each
  supported low-end device. This audit does not establish GPU performance.
- The provided screenshot is instantaneous and contains no original WAV.
  Its exact long utterance and accent were not reproduced from audio.
- Real microphone stop/cancel/paste verification, multiple low-end devices,
  macOS, Linux execution, and final release qualification remain pending.

## Validation

Frontend production build passed. All 20 frontend tests passed with one
worker; the initial parallel run had seven worker startup timeouts and
executed no tests. Backend: 61 passed, 0 failed, 1 ignored (the optional live
probe); that live probe was then explicitly invoked and passed against the
installed CLI, including nonzero CPU time, memory, and elapsed counters.
Clippy with all targets and warnings denied passed. The initial Rust compile
failed because the new metrics type lacked Deserialize; that was corrected
before these passing checks. The optimized Windows build completed
successfully. The test executable is
`outputs/whisper-performance/VibeVoice-0.2.8-whisper-pipeline-test.exe`,
SHA-256 `02bba47011136c8ab3e4afe8098ad6b97324c94d9c09a745892ba6b43a02d369`.
It uses the existing installed engine through the owner's settings.
Regression tests exercise the production stop gate,
token commit boundary, duration calculation, thread budget, CPU denominator,
settings action, and rendered measurements. A separately invoked ignored
test exercises the real installed CLI and Windows resource APIs.
