# Whisper component updater

October 3, 2026. PR branch: `codex/whisper-pipeline-v0.2.8`, based on
`codex/v0.2.8`. Initial implementation and local activation used the
`codex/pill-revamp-v0.2.8` workspace. Version 0.2.8 is unreleased.

## Delivered behavior

Settings and Diagnostics contain the same component panel. Engine updates and
model verification/repair are separate actions. Downloads run outside the UI
thread and report percentage progress. Cancel leaves previous settings intact;
a stalled response read can take up to 30 seconds to return. The HTTP client uses
an explicit per-read timeout that resets as data arrives, a separate ten-minute
overall request budget, and a 15-second connection timeout. The atomic copy also
retains its ten-minute deadline.

Only the main window can invoke the commands. A shared update lease and lifecycle
lock exclude recording starts, competing updates and settings writes. Active
recording/transcription rejects updates. Activation checks cancellation again
under the same lock and atomically writes settings. Development setup also uses
this exclusion. Production component updates do not depend on development setup,
Git, CMake, or a compiler.

The updater ships a curated, pinned recommended version. It does not resolve an
arbitrary future GitHub latest build. Future recommended versions need a catalog
update in an app release. Windows x64 and ARM64 engine packages are supported;
other platforms keep manual engine setup. Model repair is platform independent.

## Actual machine update and comparison

The updater implementation downloaded, verified and extracted the Windows x64
package, verified the existing model and transcribed the JFK sample successfully.
An independent load of its `whisper.dll` and call to `whisper_version()` returned
**1.9.4**. The prior engine still reports **1.8.6** and remains intact.

The validated candidate was activated in the actual app settings with an atomic
replacement and a timestamped settings backup. Receipts are in
`outputs/whisper-updater/installed-candidate.json`, `dll-version.json` and
`activation.json`. This is local activation, not app/release publication.

Two runs per variant on the same 11-second JFK sample, with no compiler or other
Whisper process running:

| Engine | Threads / wait | Mean wall seconds | Mean average CPU |
| --- | --- | ---: | ---: |
| 1.8.6 | Default | 3.12 | 46.8% |
| 1.9.4 | Default | 3.30 | 46.6% |
| 1.8.6 | 4 / passive | 3.07 | 41.7% |
| 1.9.4 | 4 / passive | 3.10 | 41.0% |
| 1.8.6 | 2 / passive | 4.22 | 23.4% |
| 1.9.4 | 2 / passive | 4.33 | 23.3% |

All twelve transcripts were identical, with approximately 299 MB peak working
set. Version 1.9.4 does not establish a speedup here. Earlier audit measurements
were slower on the same machine, so they must not be used as an upgrade baseline.
The two-thread setting remains the demonstrated lower CPU tradeoff. Exact logs,
timings and binary/input/DLL hashes are retained in `benchmark/` and
`old-engine-benchmark/` under the receipt directory.

## Review remediation and release-branch integration

Integrated `origin/codex/v0.2.8` at `f750748`, including PR #74. Settings saves
retain their serialized, rollback-safe transaction, engine-file validation,
hotkey/startup/topmost changes, and returned saved state. Both settings saves and
component activation acquire lifecycle then settings locks; saves reject active
component updates and clamp transcription threads to 16. Dictionary cleanup uses
the merged `prepare_transcript` helper, and the settings UI retains explicit path
save/picker behavior and command status alongside the component panel.

HTTP downloads now use the async client's separate `read_timeout(30s)` and
`timeout(600s)` settings. Request futures are constructed inside Tauri's async
runtime; hashing and atomic writes remain on the blocking update worker. This
avoids relying on the blocking client's single timeout option. See the primary
[Reqwest client timeout documentation](https://docs.rs/reqwest/latest/reqwest/struct.ClientBuilder.html#method.read_timeout).

Four real loopback HTTP regressions cover progressing transfers that outlast the
stall limit, stopped reads, total-budget exhaustion despite progress, and
cancellation after receiving data. Failed transfers preserve the working file
and remove their temporary file. The healthy test uses the same blocking worker
and async runtime arrangement as production. A separately invoked production-
timeout regression completed a progressing transfer in 33.03 seconds, exceeding
the 30-second stall limit without failing.
The updated downloader also passed the explicitly invoked real official-package
download, SHA-256 verification, startup and JFK-transcription probe again. Its
candidate receipt is retained locally as `outputs/whisper-updater/review-candidate.json`.

Integrated validation: frontend production build and 32 frontend tests passed;
75 backend tests passed with three live/long probes ignored by default. Strict
Clippy passed. Early HTTP tests caught request-future construction outside the
Tokio runtime; moving construction inside the runtime fixed it. Earlier merge
parse errors and an HTTP-fixture lint were corrected before the passing checks.
Native UI and cross-platform runtime qualification remain pending.
